## 0. 給 Claude Code 的施工守則

1. 依優先順序施工：**P0 配色 → P1 帳戶頁 → P2 方法論頁 → P3 總覽小修正**。每完成一個優先級就停下來，附截圖回報，等 Verna 確認。
2. 所有顏色只能透過 `css/tokens.css` 的 CSS 變數引用，**程式內不得出現寫死的色碼**（圖表函式庫的色彩設定也要從 tokens 讀取）。
3. 沿用 MVP 現有的圖表實作方式；需要新圖表類型時，優先用現有函式庫做得到的方式，不要為單一圖表新增依賴。若必須新增，先說明理由。
4. 新圖表需要的資料若 API 目前沒有提供，在 GAS 端新增欄位（見第 5 節），不要在前端用假資料。
5. 每張圖都要有：標題（一句結論式說明）、軸標籤／單位、滑過提示（tooltip）、無資料時的空狀態文字。
6. 不使用 AWS Logo；不模仿 AWS 主控台外觀（不使用 AWS 主控台的深藍灰 #232F3E 與 #FF9900 組合）。

這個工具是設計給 AWS 業務使用的，品牌主色應以橘色為主、黑灰白為基底、紫色為輔。

| `--ink-600` | `#4A4A4A` | 次要文字、表頭文字 |

| Token | 色碼 | 用途 | 對比限制 |
|---|---|---|---|
| `--orange-800` | `#8A4A0E` | 圖表深色系列（Security） | — |
| `--orange-700` | `#B35F12` | **連結文字、橘色文字**、白字按鈕的底色 | 白底上 ≈6.3:1，可當小字 |
| `--orange-600` | `#D2711F` | **圖表線條、點、細長條**（需 ≥3:1 的圖形元素） | 白底上 ≈3.4:1，不可當小字 |
| `--orange-500` | `#E5832F` | **主要按鈕底色、Tier 1 標章、選取中分頁底線、焦點框** | 白字在上面不夠（≈2.8:1）→ 一律配 `--ink-900` 文字（≈7.6:1） |

| `--orange-50` | `#FDF3E4` | 極淡底色（hover、提示框） | — |

**輔色：靛紫（AI 與次要資料，≤10%）**
| Token | 色碼 | 用途 |
|---|---|---|
| `--indigo-700` | `#4A2F9F` | Copilot 標題、AI 相關按鈕文字、圖表次要系列（Data） |
| `--indigo-500` | `#6B6FD4` | 圖表次要系列（GenAI） |
| `--indigo-100` | `#C0BFF6` | AI 標籤底色 |
| `--indigo-50` | `#EEEDFC` | **Copilot 面板底色**（保留：紫色 = AI 產生的內容） |

**狀態色（只在「資料狀態」頁）**：錯誤 `#C0392B`、成功 `#2E7D5B`。

### 1.3 配色原則 v2
1. **75 / 20 / 5**：中性色約 75%、橘約 15–20%、紫 ≤10%（主要集中在 Copilot 面板）。
2. **橘色 = 品牌與「要你動手」的地方**：主要按鈕、選取狀態、Tier 1。
3. **橘色深淺 = 優先度**：Tier 1 實心橘、Tier 2 淡橘、Tier 3 灰、暫緩只有框線。一眼掃過名單，越橘越該先打。
4. **紫色 = AI**：Copilot 面板、AI 產生的文字區塊、「AI 產生」標籤一律用紫色系，讓使用者分得出「系統算的」和「AI 寫的」。
5. **文字對比 ≥ 4.5:1**：橘色文字一律 `--orange-700`；`--orange-500` 只當底色（配深色字）或大面積填色。
6. **圖表元素對比 ≥ 3:1**：線、點、細條用 `--orange-600`，不用 `--orange-500`。
7. **分數變化不用紅綠**：▲▼ 箭頭＋數字；上升 `--orange-600`、下降 `--ink-500`。
8. **漸層只在品牌位置**：方法論頁頁首、字標。資料區域一律平塗。

### 2.3 各區塊規格

**A1／A2　Need、Timing 計量圖（參考：計量圖 → 基本計量圖）**
- 半圓計量圖，0–100；填色 `--orange-600`，底槽 `--gray-50`
- 中央大字分數（例：62.3），下方小字「帳戶池百分位 95」
- 計量圖弧上以 `--ink-900` 細刻度標出「前 30% 門檻」位置，一眼看出是否過線

**A3　帳戶池位置迷你象限圖（參考：散佈圖 → 平面座標圖）**

**A4　同產業排名（參考：長條圖 → 棒棒糖圖）**

**B　分數拆解：子彈圖＋帳戶池中位數（參考：組合圖 → 組合長條圖）**

  - 無資料 = 保留現有斜線紋＋「無資料」，並在右側顯示原因代碼（D18、D27），滑過顯示完整說明
- 右側數字「24.3 / 25」保留
- 說明文字改為**一行**，例如「近 12 月營收 2,107 億，池內第 95 百分位」；詳細規則移到滑過提示
- 列尾 [S#] 連結保留，最多顯示 3 個，其餘以「＋14」收合

**C　訊號時間軸：泳道點圖（參考：散佈圖＋地圖 → 點地圖的大小編碼概念）**

**E　Play 組成：百分比堆疊長條（參考：長條圖 → 百分比堆疊長條圖）**

## 3. P2：方法論頁視覺化

### 3.1 目標
現在每節都是長表格。改版原則：**每節「一句結論＋一張圖」，完整規則收進可展開區塊**。面試官 30 秒內要能看懂「資料從哪來、怎麼算、準不準」。

### 3.2 新增「30 秒摘要」（頁首橫幅下方）
4 張 KPI 卡：資料來源數｜帳戶池家數｜目前規則版本｜驗證 precision@20%（未驗證時顯示「驗證中」）

### 3.3 各節改版

**1. 資料流架構**
- 保留 5 格流程圖，每格加：線條圖示＋**本週即時數字**（例：公開資料源「6 個來源・本週 412 筆」；Sheets「訊號 1,236 則」）
- 正式上線 AWS 對照表改為**左右對照圖**：左欄本專案元件、右欄 AWS 服務，中間以箭頭連接（每列一對），取代現有表格

**2. 帳戶範圍：漏斗圖（參考：面積圖 → 漏斗圖）**
- 全部上市櫃公司 → 三產業 → 實收資本額 ≥ 10 億（185）→ 有至少 1 則訊號（n）→ Tier 1（26）
- 每層標家數與留存比例；最後一層用 `--orange-500`，其餘 `--gray-400` 由深到淺

**3. 評分規則**
- **3a 兩軸＋Tier 示意圖（參考：散佈圖 → 平面座標圖）**：一張示意象限圖，四象限標名稱與定義，取代文字說明
- **3b 權重組成：堆疊長條（參考：長條圖 → 百分比堆疊長條圖）**：兩條橫向長條，Need = N1｜N2｜N3｜N4（各 25）、Timing = T1 50｜T2 20｜T3 20｜T4 10；**點任一段展開該項規則**（手風琴），停用項目（N2、T4）以斜線紋呈現並標 D18
- **3c 計分機制小圖（參考：折線圖 → 基本折線圖）**：
  - 遞減報酬：1–5 次訊號對應 50%、75%、87.5%… 的折線
  - 時間衰減：0–30 天 ×1.0、31–90 天 ×0.5、>90 天 ×0 的階梯圖
  - 兩張小圖並排，各配一句說明
- **3d 分數分布（參考：更多圖表 → 直方圖）**：Need 與 Timing 各一張直方圖，標出 30% 門檻線，讓讀者看到門檻切在哪

**4. 關鍵字字典：樹狀圖＋熱度圖**
- **樹狀圖（參考：更多圖表 → 樹狀圖）**：方塊大小 = 本週各類別命中次數（MIG/DATA/AI/SEC/TRIG），顏色依 Play
- **熱度圖（參考：交叉表 → 熱度圖）**：列＝字典類別、欄＝三產業，格子顏色深淺 = 命中次數（`--orange-50` → `--orange-600` 單色漸層）
- 完整字典清單收進「看完整字典」展開區，可搜尋

**5. 驗證結果（參考：計量圖 → 計量圓餅圖）**
- 甜甜圈計量圖顯示 precision@20%，中央大字百分比；下方一句解讀
- 未驗證時：灰色空心圈＋「驗證集建置中」

**6. 規則版本紀錄（參考：組合圖 → 啞鈴圖）**
- 每個版本一列，啞鈴兩端 = 調整前／後的 precision，旁註「改了什麼」
- 只有 v1 時顯示時間軸單點＋「v1 基準版」

**7. 資料覆蓋與限制（參考：交叉表 → 圖形表）**
- 交叉表：列＝評分子項（N1–N4、T1–T4）、欄＝三產業，格子用圖示：✓ 可用、斜線 停用、— 不適用；滑過顯示原因（D18 就業通、D27 金融業營收）
- 其他限制改為 3–4 張圖示卡片（每張一句標題＋兩行說明），取代段落文字

### 3.4 版面
- 左側章節導覽保留，捲動時固定並高亮目前章節（`--orange-500` 左側 3px 指示條，注意：此處為導覽指示，非卡片邊框）
- 每節結構固定：章節標題 → 一句結論（16px，`--ink-900`）→ 圖 → 「看完整規則」展開區

### 3.5 驗收
- 方法論頁不展開任何區塊時，**每節最多一個表格**
- 所有圖的數字來自 API（methodology / summary），不寫死

## 4. P3：總覽頁小修正

### 4.1 「訊號不足」不再預設為 Migration（Verna 已於 2026-10-12 同意）
- **先查證再改**：動工前先用資料確認 122 家 Migration 中，有多少家的 Play 分數只來自產業先驗；把查證結果附在回報中。若原因不是產業先驗，停下來回報，不要套用下面的規則。
- **現象**：象限圖 Migration 佔 122 / 185 家，大量點集中在 Timing = 0 或 22 的直線上。推測是沒有任何 Play 訊號的公司，被產業先驗分（+5）直接判成 Migration。
- **建議規則**：若某公司 Play 分數只來自產業先驗（沒有任何實際訊號），主 Play 改為「訊號不足」，以 `--gray-400` 空心圓呈現，篩選器新增此選項。
- **好處**：Play 分布才會反映真實訊號，「Migration 很多」不會變成假洞察。
- 規則變更需將 `rule_version` 升為 v2，並在方法論頁規則版本紀錄寫明。

- 同座標的點加輕微抖動（jitter ±0.8）或改 beeswarm 排列，點透明度 70%，避免 100 多個點疊成一條線
